# 动态(朋友圈)本地缓存设计(移动端)

> 目标: 用户点开「动态」时优先用本地数据秒开，避免每次进入都打服务端；
> 首次无缓存时才回源。媒体图片随缓存一起预下载，实现弱网/离线浏览。

## 1. 分层

| 层 | 位置 | 说明 |
| --- | --- | --- |
| 列表缓存表 | `user.db` → `moment_cache` | 按 `feed`(plaza/following/mine) 缓存动态列表项 JSON，每个 feed 最多 100 条 |
| 媒体文件 | `file_record` + 本地资源目录 | 复用既有按 `biz_id` 下载链路，`biz_id` = 动态 `uuid`；物理文件落盘后离线可直接取 |
| 前端服务 | `packages/services/src/momentCache` | 读写缓存 + 后台预下载图片 |
| 页面 | `apps/mobile/src/pages/Plaza/feed/MomentFeed.vue` | 缓存优先加载、下拉刷新回源、删除同步 |

缓存表放在 **user 明文库**(`dbData/<uuid>/app.db`)：与账号天然隔离，登出时连接池关闭，换账号不会串数据。

## 2. 表结构

```sql
CREATE TABLE IF NOT EXISTS moment_cache (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  uuid TEXT NOT NULL,           -- 动态 uuid
  feed TEXT NOT NULL,           -- plaza / following / mine
  author_uuid TEXT,             -- 作者(便于按作者清理/统计)
  payload TEXT NOT NULL,        -- 列表项原始 JSON(MomentVo), 字段扩展无需改表
  created_at INTEGER DEFAULT 0, -- 动态创建时间(毫秒, 排序用)
  cached_at INTEGER DEFAULT 0,  -- 本地写入时间(毫秒)
  UNIQUE(feed, uuid)
);
CREATE INDEX IF NOT EXISTS idx_moment_cache_feed_created
  ON moment_cache (feed, created_at DESC, id DESC);
```

- 同一动态可能同时出现在 `plaza` 与 `mine`，因此唯一键是 `(feed, uuid)`。
- 写入用 `INSERT ... ON CONFLICT(feed, uuid) DO UPDATE`，重复拉取只更新内容。
- 写入后按 `created_at DESC` 裁剪到最近 `MAX_PER_FEED = 100` 条。

## 3. 加载流程

```
进入动态页
  ├─ 读本地缓存(get_moment_cache)
  │    ├─ 有缓存 → 直接渲染; 隐藏「加载更多」; 后台预下载缺失图片
  │    └─ 无缓存 → 拉服务端第 1 页 → 写缓存 → 预下载图片
  ├─ 下拉刷新(PullRefresh) → 拉服务端第 1 页 → 覆盖列表 + 更新缓存
  │    ├─ 返回空列表 → 清空该 feed 缓存
  │    └─ 失败(离线) → 保留原列表(通常是缓存), 不白屏
  └─ 加载更多(仅回源模式下可见) → 拉下一页 → 追加 + 写缓存
```

要点：

- **有缓存时不自动回源**：符合「本地有缓存需用户下拉刷新再获取」的要求。
- 缓存态下 `finished = true`，隐藏「加载更多」，避免本地数据与服务端分页混排；下拉刷新成功后恢复正常分页。
- 删除自己的动态：列表移除的同时删除缓存行（`delete_moment_cache`），重启后不会再出现。
- 发布新动态：清空 `mine` 缓存（`clear_moment_cache("mine")`），下次进入「我的」强制回源。

## 4. 媒体预下载

`prefetchMomentMedia(moments, { concurrency: 2, shouldStop })`：

- 只看 `image_count > 0` 的动态；
- 先 `hasLocalChatFile(uuid)`（本地 `file_record` + 物理文件），已存在直接跳过；
- 否则 `getFiles(uuid)` 触发 `get_file_by_biz_id` → 服务端返回预签名 URL → 落盘并写入 `file_record`；
- 并发 2，页面卸载/切换 tab 时通过 `shouldStop` 尽快停止；
- 单条失败仅记录日志，不影响其他动态与列表展示。

因为复用 `file_record`，动态图片与聊天文件共享同一套「按 biz 缓存 + 失败重试」逻辑，不重复占盘。

## 5. 已知取舍

- 缓存写入只做 upsert + 裁剪，不做全量替换：服务端已删除、但本地未主动删除的动态会一直留到被 100 条上限挤出。
- 点赞/关注等互动状态随列表 JSON 一起缓存，重新进入可能短暂显示旧状态，下拉刷新后纠正。
- 预下载为「缓存窗口内全部图片」，首次进入可能需要较多流量；后续可按网络类型（WiFi/移动网络）或总量上限做开关。
- 详情页仍走 `get_moment_detail` 实时请求，不在本次缓存范围内。
